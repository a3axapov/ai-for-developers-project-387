# PR-команда `/oc`

Инструкции для агента, который запускается комментарием `/oc` или `/opencode`
в pull request этого репозитория. Workflow
`.github/workflows/opencode.yml` пропускает команду только из PR этого же
репозитория, только от `OWNER`, `MEMBER` или `COLLABORATOR` и только не от бота;
решение принимает `scripts/pr-command-gate.mjs`. Комментарий передаёт замечания
авторевью, а не запускает бесконечный цикл: исправления делает человек-команда.

## Что прочитать перед правками

1. `AGENTS.md` и применимые `docs/agents/**`, `GLOSSARY.md`, ADR — если они есть.
2. Текст команды: перечисленные в комментарии замечания и их ID (`REV-1`, …).
3. `REVIEW.md` **из базовой ветки**, а не из головы PR:
   `git show "origin/$BASE_REF_NAME:REVIEW.md"`. Сверь критерии и формат
   замечания; `$BASE_SHA` — зафиксированный базовый commit.
4. Спецификацию и связанные тикеты, на которые ссылаются замечания.
5. Diff PR: `git diff "$BASE_SHA...HEAD"`, `git log --oneline "$BASE_SHA..HEAD"`,
   а также `gh pr view` и обсуждение PR.

Если замечание ссылается на `file:line`, проверь смысл в текущем файле: строки
могли сместиться.

## Правила

- По каждому замечанию выбери одно: исправить его либо дать обоснованный отказ
  с ссылкой на код, спецификацию или тест. Не выдумывать новые замечания и не
  переписывать несвязанный код; не выдавай косметику за исправление.
- Не мержить PR, не закрывать его и не менять состояние ревью.
- Не пушить в `main` и не делать force-push. Коммиты уходят только в head-ветку
  этого PR; не переписывай чужие коммиты и не делай rebase без просьбы.
- Оформляй исправления отдельными коммитами в стиле Conventional Commits по
  `AGENTS.md` (короткое русское описание с глаголом), по одному логически
  завершённому изменению на коммит.
- Не редактируй `REVIEW.md`, сгенерированные пути (`api/openapi/`,
  `api/server/`, `frontend/src/api/generated/`) и файлы, которыми владеют
  другие тикеты (`README.md`, `AGENTS.md`, `docs/agents/**`), если команда
  явно не просит об этом.
- Не печатай секреты и содержимое окружения.

## Проверки после правок

Сначала узкие проверки на затронутой границе, затем обязательный минимум:

- `mise run test:tools` — контрактные тесты инструментов;
- `npm run lint` — eslint, prettier и TypeSpec.

Сохрани для отчёта точные команды, **код возврата** каждой команды и
**число тестов** (например, `node --test`: 42 passed, 0 failed).

Полный `mise run check` запускай, только если правка затронула runtime-код
(Java, frontend, API, конфигурацию сборки). Если полный gate не запускался,
честно напиши это и объясни почему. Не объявляй CI успешным до зелёного прогона
на запушенном commit.

## Доказательства в комментарии PR

Итоговый ответ обработчик публикует комментарием к PR. В нём должны быть:

- таблица по каждому замечанию: ID, статус (`исправлено`, `обосновано`,
  `открыто`), commit SHA и однострочное объяснение;
- точные команды проверок, их код возврата и число тестов;
- проверенный SHA: `git rev-parse HEAD` (полный, не сокращённый);
- ссылка на CI для этого SHA: `gh pr checks <номер>` или URL run вида
  `https://github.com/<owner>/<repo>/actions/runs/<id>`;
- явный список того, что не запускалось и почему.

Фраза «тесты прошли» без команд, кодов возврата, числа тестов, SHA и ссылки на
CI доказательством не считается. Если проверка упала или недоступна, сообщи об
этом прямо и не приукрашивай результат.
