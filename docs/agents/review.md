# Процесс ревью

Ревью нужно, чтобы дефект, нарушение критериев или риск для данных были найдены
до merge. Процесс состоит из трёх независимых слоёв: внутреннее ревью
реализации, GitHub-авторевью PR и человеческое решение о merge.

## Роли

- **Автор изменения** пишет код и тесты по тикету и спецификации.
- **Внутренний ревьюер** (`implement-spec` → скилл `code-review`) проверяет
  интеграционную ветку до PR. Это отдельный проход, а не GitHub-ревью.
- **Авторевью-бот** (`opencode-review.yml`) публикует отчёт по PR. Он не
  утверждает изменение и не запускает исправления.
- **Человек-мейнтейнер** принимает решение о merge, при необходимости передаёт
  выбранные замечания командой `/oc` и фиксирует одобрение.

Реализатор изменения не является его GitHub-ревьюером. Автор не может
одобрить собственный PR: GitHub запрещает self-approval.

## Внутреннее ревью и GitHub-ревью

- **Внутреннее ревью** выполняет `implement-spec` на интеграционной ветке до
  открытия или обновления PR. Его результат — исправления и повторный прогон
  полного `mise run check`.
- **GitHub-авторевью** запускается на конкретном head-SHA PR и публикует
  комментарии. Оно не является обязательной проверкой CI и не заменяет
  человеческое решение.
- `implement-spec` не следит за комментариями бота и не реагирует на них
  автоматически. Только человек выбирает замечания и передаёт их командой
  `/oc`; правила для такой команды — в [pr-command.md](pr-command.md).
- После любой внешней правки (человек, `/oc`, другой агент) полный gate
  запускается заново на новом дереве. Старый зелёный прогон к новому SHA не
  относится.

## Триггеры, фильтр и права

GitHub-авторевью описано в `.github/workflows/opencode-review.yml`. Команда
`/oc` в PR — в `.github/workflows/opencode.yml` (задания `gate` и
`pr-command`), решение о допуске принимает `scripts/pr-command-gate.mjs`.

Авторевью запускается на `pull_request` с типами `opened`, `synchronize`,
`reopened`, `ready_for_review` и `edited`. Событие `edited` учитывается только
при изменении тела PR, а не заголовка или меток.

Проходят только нечерновиковые PR этого же репозитория от точного списка
доверенных авторов: `OWNER`, `MEMBER`, `COLLABORATOR` и
`opencode-agent[bot]`. Остальные боты (dependabot, github-actions,
release-please) и PR из fork в авторевью не попадают и уходят в ручное ревью.
Они намеренно не получают статус-комментарий: отсутствие отчёта у такого PR
означает «авторевью не запускалось», а не «замечаний нет».

Авторевью делает checkout точного `head.sha`, а не merge-ref, и читает
`REVIEW.md` и `AGENTS.md` из базовой ветки. PR не может подменить критерии
ревью, изменив эти файлы у себя. Права задания: `contents: read`,
`pull-requests: write`, `issues: write`, `actions: read`, `checks: read`,
`statuses: read`; авторизация — `GITHUB_TOKEN` (`USE_GITHUB_TOKEN: "true"`),
без `id-token`. `concurrency` по номеру PR отменяет устаревшее ревью при новом
push. Таймауты: 75 минут у job и 60 минут у шага модели.

Команда `/oc` в PR допускается только для PR этого же репозитория от `OWNER`,
`MEMBER` или `COLLABORATOR`; комментарии ботов, внешних авторов и fork PR
игнорируются. Агент пушит отдельные коммиты Conventional Commits только в
head-ветку PR, никогда в `main`, и не мержит.

## Критерии, риск и формат замечания

Критерии и шкала риска `R0`–`R3` заданы в [REVIEW.md](../../REVIEW.md). Версия
критериев берётся из базовой ветки PR. Формат замечания (`REV-N`, severity,
блокирующее, критерий, `file:line`, условие ошибки, последствие, как проверить)
тоже описан в `REVIEW.md`; замечание без `file:line`, критерия и условия ошибки
не считается замечанием.

Авторевью публикует общий комментарий ко всему изменению и inline-комментарии
к строкам diff. Замечание без возможности привязать к строке всё равно
остаётся в общем комментарии. Публикуется только `COMMENT`, без `APPROVE` и
`REQUEST_CHANGES`.

## Статусы

Статусы авторевью видны комментариями в PR, а не commit status:

- `reviewed@<sha>` — отчёт опубликован для указанного head-SHA. Это не
  одобрение.
- `limit-reached` — лимит запусков на PR исчерпан. Комментарий содержит
  причину, head-SHA и ссылку на лог; ревью этого SHA не выполнялось.
- `error` — ревью не запускалось из-за ошибки GitHub API или отчёт не
  опубликован. Отсутствие отчёта не означает отсутствие замечаний.

Отдельные commit statuses не используются: они не закрывают required-проверку
`check`, поэтому не могут быть обязательным условием merge.

## Лимит и маркеры

На PR отводится 5 попыток авторевью. Попытка резервируется скрытым
маркером-комментарием вида `<!-- review-run-limit pr=… run=… sha=… -->` до
вызова модели. Поэтому запуск, отменённый после резерва, расходует лимит, а
отменённый до резерва — нет. Маркеры считаются до вызова модели. Если список
комментариев получить не удалось, модель не вызывается и публикуется `error`.
Дополнительный запуск сверх лимита не выполняется: публикуется
`limit-reached`, и решение о merge принимает человек.

## Согласование и человеческий шлюз

Формальный approve в GitHub недоступен единственному мейнтейнеру: GitHub
запрещает self-approval. Поэтому человеческое одобрение фиксируется
комментарием к PR или к issue спецификации с явным решением и проверенным
SHA. В branch protection `required_approving_review_count` равен `0`, но PR
обязателен; остальные условия (`check`, актуальность ветки, запрет force push
и удаления, `enforce_admins`) включены.

Перед merge человек проверяет:

- точный head-SHA совпадает с тем, на который ссылаются доказательства и CI;
- `check` зелёный на этом SHA;
- замечания разобраны, блокирующих открытых нет;
- риск и откат описаны по шаблону PR.

Авторевью и `reviewed@<sha>` — доказательство, а не одобрение.

## Draft, fork и пропущенные PR

Черновики, PR из fork и PR недоверенных авторов не получают статус-комментарий
по дизайну. Их ревью выполняет человек вручную. Для fork- PR это осознанная
плата за безопасность: недоверенный код не должен попадать на раннер с
токенами и секретами.

## Bootstrap-ограничение

Workflow-файлы в `.github/workflows/` готовит и мержит человек: GitHub App
`opencode-agent` не имеет права `Workflows: write`. Воркфлоу на `issue_comment`
запускаются только с ветки по умолчанию. Поэтому bootstrap-PR с новыми
workflow должен быть смержен первым; до этого `/oc` в PR и авторевью не
работают, хотя файлы уже лежат в ветке PR.

## Остаточный риск

Если PR меняет `REVIEW.md`, `AGENTS.md`, workflow авторевью или шаблон PR,
риск выше: сам процесс ревью входит в объём изменения. Критерии читаются из
базовой ветки, поэтому подмена `REVIEW.md` в PR не меняет оценку, но изменение
workflow или шаблона авторевью проверить автоматически нельзя. В таком PR
авторевью не может быть единственным доказательством: нужен человеческий
разбор diff и отдельная проверка процесса.

## Fallback при недоступной защите

Если план GitHub или права не позволяют включить branch protection, остаётся
ручной режим: человек проверяет обязательный PR, зелёный `check` и одобрение
перед merge. Ограничение фиксируется в README и в тикете, а не выдаётся за
настроенную защиту.

## Как перепроверить защиту

Через API можно подтвердить только конфигурацию:

```bash
mise exec github-cli -- gh api \
  repos/a3axapov/ai-for-developers-project-387/branches/main/protection
```

Проверьте `required_status_checks.contexts` (`["check"]`), `strict`,
`enforce_admins`, обязательный PR, запрет force push и удаления. Что красный
или устаревший PR действительно блокирует merge, доказывает только живой PR:
создайте PR с падающим `check` или с устаревшей базой и убедитесь, что кнопка
merge недоступна; затем обновите ветку и повторите. Результат фиксируется в
тикете с точным SHA и ссылкой на PR.
