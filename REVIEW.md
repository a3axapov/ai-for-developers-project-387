# Критерии независимого ревью

Документ обязателен для авторевьюера и человека-ревьюера. Авторевью читает
`REVIEW.md` из **базовой ветки**, поэтому PR не может ослабить правила, по которым
его проверяют. Ревьюер не правит код, не продолжает реализацию и не создаёт
коммиты: его результат — отчёт о проверке.

Источники проверки: diff относительно базы, исходное обращение, спецификация,
связанные тикеты, ссылка на согласование человеком и результаты CI для точного
head-SHA. Если ссылка недоступна, раздел спецификации не найден или изменение
выходит за согласованный объём, ревьюер прямо пишет об этом в отчёте и **не
выдумывает замечания** вместо недоступного доказательства.

Отсутствие отчёта, упавший запуск или устаревший SHA не означают «замечаний нет».

## Шкала риска R0–R3

Риск определяется по последствиям ошибки, а не по размеру diff. Одна изменённая
строка в проверке конфликтов календаря может быть R3, а большой рефакторинг
текстов — R0.

| Уровень | Последствие ошибки                                                                                  | Минимальная глубина проверки                                                                        |
| ------- | --------------------------------------------------------------------------------------------------- | --------------------------------------------------------------------------------------------------- |
| R0      | Поведение продукта не меняется: документация, процесс, комментарии.                                 | Diff и доказательства автора; полный локальный gate не дублируется.                                 |
| R1      | Локальное обратимое поведение без бронирований, данных и безопасности.                              | Diff и целевая проверка затронутой границы.                                                         |
| R2      | Видимое пользователю поведение или общая бизнес-логика; данные исправимы.                           | Проверка затронутого поведения и его границ, независимый целевой прогон.                            |
| R3      | Бронирование, доступность, конфликты, идемпотентность, потеря данных, приватность или безопасность. | Полная проверка инвариантов, независимые конкурентные и граничные проверки, разбор отката и данных. |

Для R3 недостаточно зелёного CI: ревьюер проверяет, что тест действительно
воспроизводит опасное поведение, а не только проходит. Для R0 достаточно diff и
доказательств автора; повторять полный gate на неизменившемся дереве не нужно.

проверки. Ссылки на код даны в формате `file:line` и могут смещаться; ревьюер
сверяет смысл в текущем файле, а не только номер строки.

## Формат замечания

Каждое замечание оформляется одинаково в общем комментарии и в inline-комментарии
к строке diff:

| Поле           | Значение                                                                                                             |
| -------------- | -------------------------------------------------------------------------------------------------------------------- |
| ID замечания   | `REV-1`, `REV-2`, … уникален в пределах PR и сохраняется при повторном ревью                                         |
| severity       | `blocker` — дефект или риск потери данных; `major` — нарушение критерия; `minor` — качество без влияния на поведение |
| Блокирующее    | `да` или `нет`; `blocker` всегда блокирует мерж                                                                      |
| Критерий       | Ссылка на раздел `REVIEW.md` или строку таблицы критериев, спецификацию и тикет                                      |
| file:line      | Точный путь и строка изменённого файла, например `src/main/java/.../OwnerState.java:171`                             |
| Условие ошибки | Какие входные данные, состояние или гонка приводят к дефекту                                                         |
| Последствие    | Что произойдёт с пользователем, данными или календарём                                                               |
| Как проверить  | Команда или тест, воспроизводящий проблему, и ожидаемый результат                                                    |

Пример: `REV-1`, severity `blocker`, блокирующее `да`, критерий «занятый слот не
должен оставаться доступным», `OwnerState.java:171`, при двух одновременных
созданиях обе проверки видят слот свободным, последствие — двойная запись,
проверка — конкурентный тест на `TIME_CONFLICT`.

Замечание без `file:line`, критерия и условия ошибки не считается замечанием и
не передаётся в исправление. Повторное ревью помечает для каждого ID статус
`исправлено`, `обосновано` или `открыто` и указывает проверенный SHA.

## Обязательные виды комментариев

Ревью оставляет **оба вида** комментариев:

1. **Общий комментарий к PR** — итог для всего изменения: проверенный head-SHA,
   уровень риска, таблица замечаний, недоступные ссылки, выход за согласованный
   объём и вердикт.
2. **inline-комментарий к строке diff** — для каждого замечания с `file:line`,
   с тем же ID и критерием. Если блокирующих замечаний нет, inline-комментарий
   фиксирует, какая именно строка и какой критерий проверены.

Общий комментарий без inline-замечаний или inline-замечания без общего итога —
неполное ревью. Нельзя заменять один вид другим.

## Недоступные ссылки и объём

Если ссылка на спецификацию, тикет, согласование или CI недоступна, ревьюер
перечисляет её в общем комментарии как непроверенную и явно пишет, какие критерии
из-за этого не удалось подтвердить. Изменение вне согласованного объёма также
указывается отдельно. В этих случаях ревьюер **не выдумывает** замечания и не
подменяет отсутствующее доказательство предположением.

## Глубина проверки и доказательства

- Для процессных изменений (R0) достаточно diff и доказательств автора: команда,
  код выхода, число тестов и SHA. Полный локальный gate не дублируется.
- Для R1–R2 ревьюер независимо проверяет затронутую границу и граничные значения.
- Для R3 ревьюер проверяет инварианты, конкурентные сценарии, откат и влияние на
  данные; зелёный CI сам по себе не доказывает отсутствие дефекта.
- Ревьюер не запускает полный `mise run check`, JUnit и Playwright заново, если
  автор дал доказательства для того же неизменившегося дерева и точного SHA.
  Изменение дерева делает доказательства устаревшими, и об этом пишется в отчёте.
- Для процессных изменений доказательством служат diff и результаты целевых
  проверок; для runtime-изменений — полный gate и его точный SHA.
